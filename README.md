# Mini NPU Simulator

AI 가속기(NPU)의 핵심 연산인 **MAC(Multiply-Accumulate)** 을 흉내 내어, 3×3 ~ 25×25 크기의
패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 애플리케이션입니다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `re` 등)만 사용합니다. (Python 3.8+)

## 실행 방법

```bash
python main.py
```

실행하면 모드를 고릅니다.

| 선택 | 모드 | 설명 |
| :-- | :-- | :-- |
| `1` | 사용자 입력 (3×3) | 필터 A, 필터 B, 패턴을 한 줄씩(공백 구분) 입력 → 점수/시간/판정 → 3×3 성능 표 |
| `2` | data.json 분석 | 같은 폴더의 `data.json`을 읽어 일괄 판정 → PASS/FAIL → 성능 표(3·5·13·25) → 결과 요약 |

| `3` | 보너스 | 크기 N을 입력하면 N×N 십자가/X 패턴을 생성·판정하고, 2D vs 1D MAC 성능 비교 표 출력 |

- 모드 1에서 행/열 개수가 맞지 않거나 숫자가 아니면 안내 문구를 출력하고 해당 줄부터 다시 입력받습니다.
- `data.json`은 `main.py`와 같은 폴더에 두어야 하며, 실행 위치(현재 디렉터리)에 `data.json`이 있어야 합니다.
- 테스트: `python -m unittest`

### 파일 구성

| 파일 | 역할 |
| :-- | :-- |
| `main.py` | 실행 엔트리포인트, 모드 1/2 흐름, 결과 요약 출력 |
| `npu_simulator.py` | MAC 연산, 라벨 정규화, epsilon 판정, 행렬 검증 |
| `data_loader.py` | 콘솔 입력 파싱/검증, `data.json` 로드와 케이스 단위 검증 |
| `benchmark.py` | 크기별 MAC 시간 측정과 표 출력 |
| `bonus.py` | (보너스) 패턴 생성기, 1D 평탄화 MAC, 2D/1D 비교 |
| `data.json` | 필터(5/13/25)와 샘플 패턴 7개 |
| `test_phase*.py` | 단위 테스트 |

### data.json 형식

```json
{
  "filters":  { "size_5": { "cross": [[...]], "x": [[...]] }, "size_13": {...}, "size_25": {...} },
  "patterns": { "size_5_1": { "input": [[...]], "expected": "+" }, ... }
}
```

패턴 키 `size_{N}_{idx}`에서 N을 뽑아 `size_N` 필터와 연결합니다.

## 구현 요약

- **MAC 연산**: 이중 `for` 루프로 `Σ pattern[i][j] × filter[i][j]`를 직접 누적합니다 (`npu_simulator.mac`). 크기가 다르면 `ValueError`.
- **라벨 정규화**: 내부 표준 라벨은 `Cross`, `X` 두 가지입니다. expected 값과 필터 키 모두
  `+`, `cross`, `Cross`, `CROSS` → `Cross` / `x`, `X` → `X`로 바꾼 뒤 비교·출력합니다 (대소문자·앞뒤 공백 무시).
  알 수 없는 라벨은 해당 케이스(또는 해당 크기 필터)를 FAIL로 처리합니다.
- **동점 정책(epsilon)**: `abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1은 "판정 불가")를 냅니다.
  `UNDECIDED`는 어떤 expected와도 일치하지 않으므로 모드 2에서는 FAIL로 집계됩니다.
- **오류 격리**: 모드 2는 케이스마다 예외를 잡아 `FAIL + 사유`로 기록하고 다음 케이스를 계속 처리합니다.
  파일 없음·JSON 깨짐·최상위 구조 오류는 에러 메시지만 출력하고 종료 없이 돌아옵니다.
- **성능 측정**: `time.perf_counter()`로 `mac()` 호출 구간만 10회 반복해 평균(ms)을 구합니다. 입출력은 포함하지 않습니다.

## 결과 리포트

### 1. 실패 케이스 분석

현재 `data.json`(7개 케이스) 실행 결과는 **총 7개 / 통과 7개 / 실패 0개**입니다.
실패가 0이 된 이유는 세 가지 방어 정책이 각각 다른 종류의 실패를 미리 흡수했기 때문입니다.

1. **라벨/스키마 문제 → 정규화로 흡수**: expected가 `+`, `x`, `cross`, `Cross`로 제각각이고 필터 키도 `cross`/`x` 소문자입니다.
   표준 라벨(Cross/X)로 통일하지 않았다면 판정 `Cross`와 expected `+`가 문자열로 달라 **로직은 맞는데 FAIL**이 났을 것입니다.
2. **수치 비교 문제 → epsilon으로 흡수**: `size_13_3`은 잡음(0.1)이 섞인 패턴이라 X 점수가 `3.4000000000000012`처럼 부동소수점 꼬리가 붙습니다.
   점수를 `==`로 비교하면 같은 값도 다르게 보이거나 우연히 순서가 뒤집힐 수 있어, `1e-9` 허용오차 안이면 동점으로 처리합니다.
   (예: `0.1 + 0.2`와 `0.3`은 정확히는 다르지만 epsilon 안이라 동점이 됩니다.)
3. **데이터 문제 → 케이스 단위 FAIL로 격리**: 크기 불일치, `expected` 누락, 알 수 없는 라벨, 숫자가 아닌 값, 필터 누락은
   프로그램을 중단시키지 않고 해당 케이스만 FAIL로 기록하며 사유가 요약에 출력됩니다. (단위 테스트로 7종을 확인했습니다.)

실패가 생긴다면 원인은 다음처럼 분리해 진단합니다. 요약의 사유 문구가 **크기 불일치/누락/알 수 없는 라벨**이면 데이터·스키마 문제,
**판정 X != expected Y**이면 로직 또는 expected 값 문제, **동점(UNDECIDED)**이면 점수 차이가 1e-9 미만인 수치 비교 문제입니다.

### 2. 성능 표 해석과 시간 복잡도 O(N²)

MAC은 N×N 칸을 한 번씩 곱하고 더하므로 **연산 횟수는 정확히 N²** 이고, 시간은 이에 비례하는 **O(N²)** 입니다.
아래는 이 개발 환경(Python 3.14, Windows)에서 같은 크기를 2000회 반복해 얻은 평균 시간의 한 예입니다.

| 크기 | 연산 횟수(N²) | 평균 시간(ms) | 연산 1회당 시간(µs) |
| :-- | --: | --: | --: |
| 3×3 | 9 | 0.0025 | 0.28 |
| 5×5 | 25 | 0.0045 | 0.18 |
| 13×13 | 169 | 0.029 | 0.17 |
| 25×25 | 625 | 0.090 | 0.14 |

- 13×13 → 25×25는 연산 횟수가 약 3.7배(625/169)인데 시간은 약 3.1배(0.090/0.029)로, N²에 가깝게 증가합니다.
  5×5 → 13×13도 연산 횟수 6.8배, 시간 6.4배로 비슷합니다. 즉 연산 1회당 시간이 거의 일정(0.14~0.18µs)하다는 뜻이며, 이것이 O(N²)의 근거입니다.
- 3×3에서 연산 1회당 시간이 더 큰 것은 **함수 호출·루프 설정 같은 고정 오버헤드**가 연산 9번에 나뉘어 상대적으로 크게 보이기 때문입니다.
  크기가 커질수록 이 고정 비용이 희석되어 N² 비례에 가까워집니다.
- 기본 측정(10회 평균)은 마이크로초 단위의 짧은 구간이라 실행마다 값이 꽤 흔들립니다. 실제로 3×3과 5×5의 순서가 바뀌어 보이는 경우도 있으며,
  이는 타이머 해상도와 OS 스케줄링 잡음 때문이지 N² 관계가 깨진 것은 아닙니다. 반복 횟수를 늘리면 위 표처럼 추세가 안정됩니다.
- 시사점: 필터가 수백×수백으로 커지면 N²배로 연산량이 폭증하므로, 곱셈을 병렬로 동시에 처리하는 NPU가 필요해집니다.
  이 시뮬레이터는 모든 MAC을 순차 실행하므로 시간이 연산 횟수에 그대로 비례합니다.

## 보너스 결과

### 패턴 생성기

`bonus.generate_cross(n)` / `generate_x(n)`이 N×N 십자가(가운데 행·열)와 X(두 대각선) 패턴을 만듭니다.
모드 3의 판정과 2D/1D 비교의 입력으로 재사용되며, N=3일 때 미션의 예시 패턴과 동일합니다.
(N이 짝수이면 십자가의 중심선은 `N//2`번째 행/열입니다.)

### 2D vs 1D MAC 비교

`mac_1d`는 2차원 리스트를 길이 N²의 1차원 리스트로 평탄화한 뒤 단일 `for` 루프로 누적합니다.
동일한 입력(Cross 패턴 × X 필터), 동일한 반복 횟수로 측정하며, 평탄화 변환 자체는 측정 구간 밖에서 한 번만 수행합니다.
두 방식의 점수가 같은지도 매번 확인합니다. 이 환경에서 2000회 반복한 결과 예시:

| 크기 | 2D(ms) | 1D(ms) | 2D/1D |
| :-- | --: | --: | --: |
| 3×3 | 0.0023 | 0.0013 | 약 1.7x |
| 5×5 | 0.0058 | 0.0030 | 약 1.9x |
| 13×13 | 0.029~0.034 | 0.024 | 약 1.2~1.4x |
| 25×25 | 0.093~0.122 | 0.067~0.081 | 약 1.4~1.5x |

1D가 대체로 1.2~2배 빠릅니다. 이중 루프의 안쪽 루프 설정과 `pattern[i][j]`의 두 번 인덱싱이 사라져
인덱싱·루프 오버헤드가 줄기 때문입니다. 다만 연산 횟수(N²)는 같으므로 시간 복잡도는 두 방식 모두 O(N²)이고,
이득은 상수 배수에 그칩니다. 측정값은 실행마다 흔들리므로 위 수치는 경향으로만 봐야 합니다.

## 대규모 입력(1000×1000)의 메모리·최적화 분석

필터 크기가 1000×1000으로 커지면 한 번의 MAC이 **1,000,000회 곱셈**이고, 행렬 하나가 차지하는 메모리도 N²에 비례합니다.
아래 수치는 이 환경(Python 3.14, Windows)에서 직접 측정한 값이며, 측정 코드는 저장소에 포함하지 않은 일회성 스크립트입니다.
값은 실행마다 달라지므로 절대값이 아니라 경향으로 읽어 주세요.

### 메모리

| 표현 방식 | 25×25 | 100×100 | 1000×1000 |
| :-- | --: | --: | --: |
| 2차원 리스트(컨테이너만) | 7 KB | 90 KB | 약 8.5 MB |
| 1차원 리스트(컨테이너만) | 5 KB | 83 KB | 약 8.1 MB |
| `array('d')` (8바이트 실수 연속 배열) | 4 KB | 78 KB | 약 7.6 MB |

- 위 표는 리스트가 들고 있는 **참조(8바이트) 배열**의 크기입니다. 값이 서로 다른 `float`이면 값마다 별도 객체(약 24바이트)가 더 필요해서,
  1000×1000 한 행렬이 약 8 MB + 약 23 MB ≈ **30 MB 이상**이 되고 패턴과 필터를 합치면 두 배입니다.
  `data.json`처럼 0/1 정수만 쓰면 CPython이 작은 정수 객체를 공유하므로 참조 배열 몫(행렬당 약 8 MB)에 가깝습니다.
- 시간과 메모리 모두 **O(N²)** 이므로, 큰 N에서는 "연산이 느리다"와 "데이터가 크다"가 함께 문제입니다.

### 대형 입력에서 측정된 시간 (1회 MAC)

| 방식 | 25×25 | 1000×1000 |
| :-- | --: | --: |
| 2D 이중 루프 (`mac`) | 약 0.04~0.16 ms | 약 94~138 ms |
| 1D 평탄화 리스트 (`mac_1d`) | 약 0.03 ms | 약 116 ms |
| `array('d')` + `mac_1d` | 약 0.05 ms | 약 318 ms |
| **희소(비제로 칸만 곱함)** | **약 0.007 ms** | **약 0.9 ms** |

- 연산 1회당 시간은 1000×1000에서도 약 0.09~0.14 µs로 25×25와 거의 같습니다. 즉 이 구현에서는 **캐시 미스로 인한 급격한 둔화가 관측되지 않았고**,
  파이썬 인터프리터의 루프·객체 접근 비용이 지배적입니다. 캐시·메모리 레이아웃의 효과는 컴파일 언어나 SIMD 환경에서 훨씬 크게 나타납니다.
- 1D 평탄화는 작은 N(3~25)에서 1.2~2배 빨랐지만 **1000×1000에서는 이득이 사라졌습니다**. `array('d')`는 메모리는 줄이지만,
  원소를 읽을 때마다 `float` 객체를 새로 만들어야 해서 오히려 느렸습니다. 메모리 절감이 곧 속도 향상은 아닙니다.
- 희소 방식은 필터에서 0이 아닌 칸의 위치와 값만 모아 두고 그 칸들만 곱합니다. 결과 점수는 밀집 방식과 동일함을 확인했습니다.
  Cross/X 필터는 비제로가 약 2N개(1000×1000에서 2000개, 전체의 0.2%)뿐이라 연산이 N²에서 O(N)으로 줄어듭니다.
  비제로 목록을 만드는 비용(O(N²))은 필터당 한 번이고 여러 패턴에 재사용할 수 있어 위 시간에 포함하지 않았습니다.

### 최적화 우선순위

| 순위 | 항목 | 기대 효과 | 근거 / 한계 |
| :--: | :-- | :-- | :-- |
| 1 | **희소성 활용** (0인 칸 건너뛰기) | 이 과제의 필터에서 연산량 N² → O(N), 1000×1000에서 약 150배 | 측정함(미구현). 실제 AI 필터는 대부분 밀집이라 일반화되지 않음 |
| 2 | **메모리 평탄화·연속 배치** | 접근 패턴 단순화, 캐시 적중률 향상 | 이 파이썬 구현은 큰 N에서 이득이 없음을 측정함. 컴파일 언어에서 의미가 큼 |
| 3 | **데이터 크기 축소** (0/1 데이터는 1바이트 등) | 메모리 8~32배 절감 가능 | 이론적 추정, 미측정. 파이썬에서는 접근 비용 때문에 속도 향상 보장 못 함 |
| 4 | **블록(타일) 연산** | 한 번에 캐시에 들어오는 조각만 처리 | 필터를 한 번만 훑는 MAC은 재사용이 없어 이득이 작음. 여러 필터를 겹쳐 쓰는 합성곱에서 의미가 큼 (미구현) |
| 5 | **병렬화** | N²개의 곱셈은 서로 독립 → P개 유닛이면 이상적으로 ⌈N²/P⌉단계 + 합산 | CPython은 GIL 때문에 스레드로는 가속이 안 되고, 프로세스는 데이터 전달 비용이 큼. NPU/SIMD가 본격적인 해법 (미구현) |

정리하면, 이 시뮬레이터에서 먼저 줄여야 할 것은 "곱셈 횟수" 자체(희소성)이고, 메모리 레이아웃·블록화는 하드웨어와 언어에 따라 효과가 크게 갈립니다.
CPU가 N²개의 MAC을 하나씩 순서대로 처리하는 동안, NPU는 P개의 MAC 유닛으로 한 번에 처리하므로 이론상 걸리는 단계 수가 약 1/P로 줄어듭니다
(예: 25×25의 625회 MAC을 625개 유닛이 처리하면 곱셈 1단계). 이는 이상적인 계산이며 합산과 데이터 이동 비용은 포함하지 않았습니다.

## 설계 참고

### 모드별 판정 정책

| 구분 | 모드 1 (사용자 입력) | 모드 2 (data.json) |
| :-- | :-- | :-- |
| 비교 대상 | 필터 A 점수 vs 필터 B 점수 | Cross 필터 점수 vs X 필터 점수 |
| 판정 값 | `A` / `B` / 판정 불가 | `Cross` / `X` / `UNDECIDED` |
| 동점(`abs(a-b) < EPSILON`) | "판정 불가 (\|A-B\| < 1e-9)" 출력 | `UNDECIDED` → expected와 같을 수 없으므로 **FAIL** |
| PASS/FAIL | 없음 | 판정 == 정규화된 expected 이면 PASS |

점수 비교 원칙: 점수가 **더 큰 쪽**이 더 유사하다고 보며, 임계값을 따로 두지 않고 두 점수의 차이가 EPSILON 미만일 때만 동점으로 처리합니다.

### MAC 의사코드

```
score = 0
for i in 0..N-1:
    for j in 0..N-1:
        score += pattern[i][j] * filter[i][j]     # N² 번 실행 → 시간 복잡도 O(N²)
return score
```

### 입력 형식과 단위

- 모드 1 입력은 한 줄에 숫자 3개를 공백으로 구분합니다. 예: `0 1 0`
- 모든 시간은 **ms(밀리초)** 입니다. 모드 1의 `연산 시간(평균/10회): 0.001 ms`와 성능 표의 `평균 시간(ms)` 열이 같은 단위입니다.
- 성능 표의 `반복` 열은 평균을 낸 반복 횟수(기본 10)이며, 같은 값이 표 제목 `(평균/10회)`에도 표시됩니다.

### 라벨 정규화 표

| 입력 (expected 값 / 필터 키) | 표준 라벨 |
| :-- | :-- |
| `+`, `cross`, `Cross`, `CROSS` | `Cross` |
| `x`, `X` | `X` |

`normalize_label`의 경계 동작: 앞뒤 공백은 제거하고 대소문자는 구분하지 않습니다(`" Cross "` → `Cross`).
`plus`, `xx`, 빈 문자열은 `ValueError("알 수 없는 라벨")`, 문자열이 아닌 값(`None`, `5`)은 `ValueError("라벨이 문자열이 아닙니다")`를 냅니다.
모드 2에서는 이 예외가 케이스(또는 필터) 단위 FAIL로 바뀝니다.

**새 라벨을 지원하려면**: ① `npu_simulator._LABEL_MAP`에 `소문자 입력: 표준 라벨` 한 줄을 추가하고
② `test_phase1.py`의 `test_normalize`에 케이스를 더한 뒤 ③ 위 표를 갱신합니다. 표준 라벨 자체(Cross/X)를 늘릴 때는 `parse_filters`와 `evaluate_pattern`도 함께 수정해야 합니다.

### 패턴 키 규칙과 오류 예시

패턴 키는 정규식 `^size_(\d+)_(\d+)$`로 해석하며 첫 번째 그룹이 크기 N, 두 번째가 일련번호입니다. 대소문자를 구분합니다.

| 키 | 결과 |
| :-- | :-- |
| `size_5_1` | N=5, `size_5` 필터와 매칭 |
| `size_5` | FAIL: `키 형식 오류 (size_{N}_{idx} 필요)` (idx 없음) |
| `Size_5_1` | FAIL: 같은 사유 (대문자 `S`) |
| `size_5_a` | FAIL: 같은 사유 (idx가 숫자가 아님) |
| `size_7_1` (필터에 `size_7` 없음) | FAIL: `size_7 필터가 없습니다.` |

### EPSILON 조정

허용오차는 `npu_simulator.EPSILON = 1e-9` 상수 하나로 정의되고, `judge()`와 `is_tie()`가 기본값으로 참조합니다.
전역 값을 바꾸지 않고 호출마다 다르게 쓸 수도 있습니다.

```python
from npu_simulator import EPSILON, judge
judge(0.9, 0.8999999999999999)              # 'UNDECIDED' (기본 EPSILON = 1e-9)
judge(1.0, 1.0005, epsilon=1e-3)            # 'UNDECIDED' (허용오차를 1e-3으로 넓힘)
judge(1.0, 1.0005, "Cross", "X")            # 'X' (기본값에서는 차이가 EPSILON보다 큼)
```

### 성능 측정 방식

`measure_avg_ms`는 **워밍업 호출 없이** `mac()`을 지정한 횟수(기본 10회) 그대로 측정해 평균을 냅니다. 첫 호출도 평균에 포함됩니다.
측정 구간이 마이크로초 단위로 짧아 첫 호출 비용이나 OS 스케줄링 때문에 값이 흔들리며, 이 때문에 README의 비교 표는 2000회 반복한 값을 따로 인용했습니다.
작은 N(3×3 등)에서는 함수 호출·루프 설정 같은 고정 오버헤드가 연산 몇 번에 나뉘어 연산당 시간이 더 크게 보입니다.
